# P0.4 · Base jurídica com atualização diária: o que foi integrado

Documento de decisão da integração do pacote recebido em
`docs/referencia/rag-juridico-diario/` (prompt original em
`docs/P0.4-rag-diario-prompt.md`).

O pacote foi mantido byte-a-byte na pasta de referência, sem alteração, para
que dê para comparar o que foi entregue com o que de fato entrou no projeto.
Ele está fora do `tsconfig.json` e do ESLint: não compila (usa
`@vercel/postgres`, que este projeto não tem) e não é código do app.

## Resumo da decisão

O prompt pedia "integrar, não escrever do zero". O ponto que muda tudo é que
o pacote foi desenhado para um projeto **sem RAG**, e este projeto **já tem
um RAG maduro em produção**. Colar os arquivos como vieram criaria uma
segunda base vetorial paralela à existente. Então: o **pipeline conceitual**
do pacote foi adotado inteiro, e a **implementação** foi reescrita sobre a
stack real.

### O que o pacote assumia vs. o que o projeto tem

| Pacote recebido | Projeto real |
|---|---|
| `@vercel/postgres` com `sql` template | Supabase (`@supabase/supabase-js`), RLS multi-tenant |
| OpenAI `text-embedding-3-small`, 1536 dim | Gemini `gemini-embedding-001`, 768 dim (`lib/rag/embeddings.ts`) |
| Nova tabela `base_juridica` | `embeddings_chunks` (migrations 0002/0008/0029/0037) |
| `consultarBaseJuridica()` novo | `buscarContextoRelevante()` já existente |
| `buscarAtualizacoesDJEN()` a escrever | `lib/djen/sincronizar.ts`, em produção |
| Jurisprudência a definir | `lib/jurisprudencia/stj.ts`, dados abertos STJ (CC-BY), 865 acórdãos já ingeridos |
| Chunking por 500 palavras | `lib/rag/chunking.ts`, recursivo por parágrafo/frase |

### Por que NÃO criar a tabela `base_juridica`

`embeddings_chunks` carrega duas garantias que uma tabela nova não teria de
graça, e cuja ausência é um vazamento entre escritórios:

- CHECK `chk_embeddings_escritorio_por_fonte` (migration 0008): chunk
  compartilhado obriga `escritorio_id IS NULL`, chunk de tenant obriga
  `escritorio_id NOT NULL`.
- `buscar_chunks_similares` é `security definer` e filtra
  `escritorio_id = p_escritorio_id OR escritorio_id IS NULL` **dentro da
  função**, não só por RLS.

O `consultar-rag.ts` do pacote não tem nenhum conceito de escritório: um
`SELECT ... FROM base_juridica` sem filtro de tenant. Para conteúdo público
isso é correto, mas o retrieval do produto passaria a ter dois caminhos com
regras de isolamento diferentes.

## O que foi de fato implementado

### 1. Migration `0048_rag_execucao_e_cursor.sql`

- `rag_fonte_cursor` · checkpoint por fonte, com **timestamp** (não `DATE`),
  marcado no **início** da busca. É exatamente a correção que o pacote pedia
  para não regredir, e ela não existia aqui para o DJEN.
- `rag_execucao_log` · histórico append-only por fonte
  (`sucesso` / `sucesso_parcial` / `erro` / `pulado`), com contadores,
  duração e mensagem de erro. Antes o rastro era `console.error` na Vercel,
  que some com a retenção.
- `rag_saude_fontes()` · RPC que devolve, por fonte, a última execução e o
  último **sucesso**, em uma chamada.
- RLS: leitura para `authenticated`, escrita só `service_role` (cron).

### 2. `lib/rag/execucao.ts`

Cursor (`lerCursorFonte` / `avancarCursorFonte`), log (`registrarExecucaoRag`)
e saúde (`lerSaudeFontesRag` / `montarSaudeFonte`). A regra do alerta é uma
função pura, testada em `lib/rag/execucao.test.ts`.

Limite do alerta: **26h**, não 24h. Um cron diário que atrasa alguns minutos
não pode gerar alerta falso, senão o alerta perde credibilidade e passa a ser
ignorado, que é pior do que não ter alerta.

### 3. `lib/rag/fontes-diarias.ts`

Registro central das fontes. Cada entrada é um adaptador fino sobre um
pipeline que já existe: `djen` e `stj_dados_abertos`. Não reimplementa busca,
chunking, embedding nem deduplicação.

O STJ passa a ser consultado **diariamente** (antes: mensal, dia 3). Como
`sincronizarOrgaoStj` só baixa quando o arquivo é mais recente que o
registrado em `fontes_stj_sync.ultimo_arquivo`, 29 dos 30 dias custam apenas
a leitura de metadados do CKAN · em troca, o mês novo entra na base no dia em
que é publicado.

### 4. `app/api/cron/atualizar-base-juridica/route.ts`

Orquestrador diário (5h UTC). Isola falha por fonte, avança o cursor só quando
a fonte terminou sem exceção, grava uma linha por fonte no log e, no fim,
checa a saúde de todas e dispara alerta.

Execução **sequencial**, não `Promise.all`: as fontes competem pela mesma cota
de embedding do Gemini e pelo mesmo pool de conexões.

Status HTTP: 200 mesmo com erro parcial (o corpo diz o que falhou); 500 só
quando nenhuma fonte passou, que é o que faz o Vercel Cron marcar a execução
como falha no painel.

### 5. `lib/rag/alerta.ts` · o item que faltava do critério de aceite

Dois canais:

1. `console.error` com `evento: "rag_base_juridica_desatualizada"` · gancho
   estável para regra de alerta no log drain, sempre emitido.
2. Webhook HTTP genérico via env var **`RAG_ALERTA_WEBHOOK_URL`** (POST JSON
   com campo `text`: Slack, Discord, Teams). Escolhido em vez de acoplar a um
   provedor porque o canal do time é decisão de operação · plugar vira
   preencher uma env var, sem mudar código.

Sem a env var, o retorno diz `canalWebhookConfigurado: false` em vez de fingir
que notificou.

### 6. RAG plugado no Advogado do Contra

Até aqui, **só o chat** consultava o RAG. Todas as outras features de IA
montavam o prompt sem base · é o gap que o P0.4 chama de risco jurídico.

- `lib/rag/contexto-juridico.ts` · ponte para features fora do chat. Restringe
  a busca a `fonte_tipo = 'jurisprudencia'` (contra-argumentar uma tese com a
  ficha interna do próprio caso seria circular) e anexa instrução explícita de
  citar fonte/data do trecho, com proibição de inventar processo/relator/data.
- `lib/rag/retrieval.ts` ganhou o parâmetro opcional `fonteTipos` (a RPC já
  aceitava `p_fonte_tipos`; só não estava exposto).
- `app/app/advogado-contra/actions.ts`: modos **colado** e **tese_cadastrada**
  agora recuperam contexto antes de montar o prompt.

O bloco recuperado entra **depois** do texto a analisar, como bloco separado e
delimitado (`montarBlocoContexto`, marcado como não confiável), para não
misturar o alvo da análise com a referência recuperada.

### 7. `vercel.json`

Passou a ter **duas** entradas em vez de três:

```
/api/cron/atualizar-base-juridica  0 5 * * *
/api/cron/lembretes-whatsapp       0 12 * * *
```

- `/api/cron/sincronizar-djen` saiu do agendamento: o orquestrador já roda o
  DJEN todo dia às 5h. Manter as duas entradas sincronizaria o DJEN duas vezes
  por dia sem ganho. A rota continua existindo para disparo manual.
- `/api/cron/sync-stj` saiu pelo mesmo motivo, **e porque nunca funcionou
  como cron**: a rota só exportava `POST`, e o Vercel Cron dispara sempre
  `GET`. Toda execução agendada respondia 405 desde que foi criada; o único
  sync que aconteceu foi o manual (ver `PENDENCIAS.md` §1.3). Foi adicionado
  `export const GET = POST` para o disparo por URL funcionar.

## O que NÃO foi feito, e por quê

**Fonte de legislação (LexML / Planalto).** O pacote previa
`buscarAtualizacoesLegislacao()` com dados de exemplo. Não foi plugada, e o
slot está **ausente** do registro em vez de presente-e-mockado: uma fonte
registrada devolvendo conteúdo de exemplo entraria no `embeddings_chunks`
real e viraria "contexto jurídico atualizado" citável pela IA dentro de uma
peça. Mesmo critério já adotado em `lib/rag/jurisprudencia.ts`.

Para virar uma entrada em `FONTES_DIARIAS` precisa de: (1) confirmação de que
a fonte devolve texto consolidado e não só metadados, (2) parser dedicado por
formato, (3) decisão sobre licença de redistribuição.

**RAG no modo `upload` do Advogado do Contra.** O texto do PDF/DOCX só é
extraído dentro de `analisarComoAdvogadoContra`, então na action ainda não
existe a consulta a fazer. O título sozinho é sinal fraco demais para uma
busca por similaridade útil, e busca ruim devolve precedente irrelevante com
cara de fundamentado. Plugar exige mover a extração para fora de
`lib/advogado-contra/analisar.ts`.

**Idempotência por `event.id` no webhook do Stripe.** Uma entrega duplicada
hoje é inofensiva (o `upsert` é por `escritorio_id` e o update é por
`stripe_subscription_id`), então uma tabela de eventos processados seria
custo sem risco correspondente.

## Passos manuais para ativar

1. Aplicar `supabase/migrations/0048_rag_execucao_e_cursor.sql` (depende de
   0037–0047 já estarem aplicadas · ver `docs/MIGRATIONS_PENDENTES.md`).
2. Opcional: definir `RAG_ALERTA_WEBHOOK_URL` na Vercel (Slack/Discord). Sem
   ela o alerta fica só no log.
3. Deploy. Testar manualmente antes de confiar no cron:
   ```bash
   curl -H "Authorization: Bearer $CRON_SECRET" \
     https://juridico-ia-saas.vercel.app/api/cron/atualizar-base-juridica
   ```
4. Conferir no banco:
   ```sql
   select fonte, status, documentos_novos, duracao_ms, executado_em
     from rag_execucao_log order by executado_em desc limit 20;
   select * from rag_fonte_cursor;
   select * from rag_saude_fontes();
   ```
5. Cron só dispara em **produção**, nunca em preview deployment.

## Critério de aceite do P0.4

| Critério | Estado |
|---|---|
| Job roda automaticamente todo dia sem intervenção | ✅ `vercel.json`, 5h UTC |
| `rag_execucao_log` mostra execuções, falhas nunca silenciosas | ✅ migration 0048 + `registrarExecucaoRag` |
| Ao menos um módulo de IA consulta o RAG e cita fonte/data | ✅ Advogado do Contra (colado e tese cadastrada); chat já fazia |
| Alerta se o job falhar por mais de 24h | ✅ `lib/rag/alerta.ts`, limite 26h · canal real pende de `RAG_ALERTA_WEBHOOK_URL` |
| Fonte de legislação plugada | ❌ decisão de fonte pendente, ver acima |
