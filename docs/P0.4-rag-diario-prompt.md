# Prompt de Implementação — Base de Conhecimento Jurídico com Atualização Diária (RAG)

## Contexto

Você vai integrar ao projeto **Jurídico IA** (https://juridico-ia-saas.vercel.app/) um pipeline que mantém a base de conhecimento jurídico da plataforma sempre atualizada, para que os módulos de IA (score de persuasão, advogado do contra, geração de peça, sugestão de tese, etc.) não dependam só da memória "congelada" do modelo de linguagem — eles vão consultar uma base própria, atualizada todos os dias, com jurisprudência, legislação e movimentações recentes.

Isso corresponde ao item **P0.4** do backlog do projeto (prioridade alta — risco jurídico se ausente).

Os arquivos já vêm prontos no zip `rag-juridico-diario.zip`, organizados na estrutura de pastas do Next.js App Router. Sua tarefa é integrar, não escrever do zero.

## Arquivos que você recebeu e o que fazer com cada um

| Arquivo | O que é | Ação necessária |
|---|---|---|
| `schema-rag.sql` | Cria as tabelas no Postgres (base de conhecimento vetorial + checkpoint + log de auditoria) | Rodar uma vez no banco do projeto. Requer extensão `pgvector` disponível (Vercel Postgres/Neon/Supabase já suportam). |
| `lib/embeddings.ts` | Transforma texto em vetor via API da OpenAI | Nenhuma mudança necessária, só garantir a env var abaixo. |
| `lib/fontes-juridicas.ts` | Onde ficam as buscas por fonte (DJEN, tribunais, legislação) | **Precisa de trabalho real aqui** — está com dados de exemplo. Ver seção "O que só vocês conseguem fazer" abaixo. |
| `app/api/cron/atualizar-base-juridica/route.ts` | O job que roda todo dia | Nenhuma mudança de lógica necessária, só configurar as env vars. |
| `lib/consultar-rag.ts` | Função que os módulos de IA existentes vão chamar para buscar contexto atualizado | Integrar dentro dos módulos de IA já existentes (ver seção de integração abaixo). |
| `vercel.json` | Configura o cron para rodar todo dia às 5h | Se o projeto já tiver um `vercel.json`, mesclar o bloco `crons` nele em vez de sobrescrever. |

## Passo a passo de implementação

1. **Banco de dados**: rodar `schema-rag.sql` no Postgres do projeto. Confirmar que a extensão `pgvector` foi criada sem erro antes de seguir.

2. **Variáveis de ambiente**: adicionar no projeto (Vercel → Settings → Environment Variables):
   - `OPENAI_API_KEY` — chave da API da OpenAI, usada para gerar os embeddings.
   - `CRON_SECRET` — qualquer string aleatória forte; a Vercel usa isso automaticamente para autenticar a chamada do cron (não precisa configurar nada além de criar a env var).

3. **Plugar as fontes jurídicas reais** em `lib/fontes-juridicas.ts`:
   - `buscarAtualizacoesDJEN()` — reaproveitar a integração com DJEN que o projeto já tem (via `monitor-processual.jsx`, citada no levantamento original do produto), em vez de criar uma busca nova do zero.
   - `buscarJurisprudenciaTribunaisSuperiores()` — decidir a fonte real (API pública do STJ/STF, ou um fornecedor de jurimetria) e substituir o mock.
   - `buscarAtualizacoesLegislacao()` — decidir a fonte real (ex: LexML, Planalto) e substituir o mock.
   - Cada função só precisa devolver dados no formato `DocumentoJuridico` já definido no arquivo — o resto do pipeline (chunking, embedding, deduplicação, salvamento) já funciona sem precisar mexer em mais nada.

4. **Integrar `consultarBaseJuridica()` nos módulos de IA já existentes** (score de persuasão, advogado do contra, e qualquer módulo novo que gere texto jurídico): antes de montar o prompt que vai para o modelo de IA, chamar essa função com a pergunta/contexto do caso, e injetar o resultado no prompt como contexto adicional, citando fonte e data. Tem um exemplo comentado dentro do próprio `lib/consultar-rag.ts`.

5. **Testar manualmente antes de deixar o cron automático assumir**: chamar a rota `/api/cron/atualizar-base-juridica` direto (com o header `Authorization: Bearer <CRON_SECRET>`) e confirmar no banco que linhas novas apareceram em `base_juridica` e que `rag_execucao_log` registrou `status = 'sucesso'`.

6. **Confirmar que o cron está ativo** depois do deploy — a Vercel só dispara cron jobs em produção, não em preview deployments.

## Critério de aceite (quando considerar isso pronto)

- Job roda automaticamente todo dia sem intervenção manual.
- `rag_execucao_log` mostra execuções com `status = 'sucesso'` (ou `sucesso_parcial` com falhas pontuais registradas, nunca silenciosas).
- Pelo menos um módulo de IA do produto já consulta `consultarBaseJuridica()` antes de gerar texto e cita a fonte/data da informação usada na resposta.
- Se o job falhar por mais de 24h seguidas, alguém do time é notificado (esse alerta ainda precisa ser plugado no canal de notificação real do time — está sinalizado como próximo passo dentro do código, na função de erro do `route.ts`).

## O que NÃO fazer

- Não recriar a lógica de chunking, deduplicação ou geração de embeddings — já está pronta e testada (passou por três rodadas de revisão técnica).
- Não trocar `MAX(data_publicacao)` de volta como cursor de incrementalidade — foi trocado por `rag_fonte_cursor` de propósito, porque a coluna de data sozinha não tem granularidade suficiente se o job um dia rodar mais de uma vez ao dia.
- Não remover o `ON CONFLICT (hash_conteudo) DO NOTHING` do insert — é o que evita duplicar conteúdo no banco.
